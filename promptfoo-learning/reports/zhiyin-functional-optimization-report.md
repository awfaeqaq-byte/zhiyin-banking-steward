## 2. 测试用例如何生成

测试用例不是由模型随机生成后直接相信结果，而是从四类事实反推：

1. 产品规则：提示词中关于数据来源、风险测评、确认流程和禁止保证收益的约束。
2. 代码能力：`parseStewardReply` 支持的动作类型、参数格式和前端处理路径。
3. 业务不变量：核对不扣款、确认才扣款、金额守恒、重复确认不得重复扣款、赎回后资金和持仓一致。
4. 已发现问题：净资产误述、回答截断、多轮条件变化后建议未及时更新等。

每条用例由输入、预期行为和断言组成。格式、金额和安全边界使用 JavaScript/正则等确定性断言；复杂语义使用 `glm-5.3` 的 `llm-rubric` 评分。资金状态由应用自身测试直接断言，不交给评分模型猜测。

## 4. 已实施的优化

### 4.1 评分模型独立化

四套 Promptfoo 配置的语义评分器已从 `glm-5.2` 改为 `glm-5.3`，温度固定为 0。知银目标模型仍是当前配置的 `glm-5.2`，避免同一个模型直接评价自己的回答。

### 4.2 回答完整性保护

知银服务端代理现在会：

1. 读取上游 `finish_reason`。
2. 将 `finish_reason=length` 或长回答停在半句视为疑似截断。
3. 自动重试一次，并明确要求完整句子或合法结构化标记结尾。
4. 第二次仍不完整时返回错误，不展示半句话。
5. 在同源接口中返回 `finish_reason` 和 `completeness_retried`，便于 debug。

在线 F06 探针结果：HTTP 200，`finish_reason=stop`，`completeness_retried=true`，最终回答 244 字；回答拒绝保证收益，并要求风险测评和单独确认。说明运行中的服务确实触发了重试，而不只是单元测试通过。

### 4.3 净资产确定性约束

财务教练提示词已加入明确规则：债务或外部资产不完整时，禁止输出“净资产为/是 X”，禁止把未知负债写成 0 或“暂记为 0”；只能说明已知局部余额并声明完整净资产无法计算。

F05 同时保留正则断言，避免评分模型因措辞自然但结论错误而放行。

### 4.4 多轮逐轮完整性断言

F03、F04 不再只检查最后一轮。测试会确认三轮助理回答都存在，长回答必须以完整句号、问号、感叹号或合法结构化标记结束。

### 理财：9/9

覆盖五项风险测评的亏损承受上限、产品不能越级、申购前不扣款、确认后余额与持仓一致、重复确认只有一笔回执、余额不足/旧测评/过期方案不产生持仓、封闭期拒绝赎回、开放后赎回入账以及历史账本迁移。

这些测试在 Node + Vitest + jsdom 中运行，不打开浏览器。服务层测试证明业务状态变化，组件测试模拟用户核对和确认过程。它们不能发现 CSS 遮挡、真实浏览器焦点、触摸事件或页面跳转问题；只有要验证这些浏览器特有风险时才需要 Playwright 或人工浏览器测试。

## 6. 快捷选项、动作和真实功能的关系

`[[choices:...]]` 只是下一轮用户消息。解析器限制为 2 至 3 项、去重、每项不超过 30 字；点击后发送文字，不构成资金授权。

`[ZHIYIN_ACTION:...]` 才是模型提出的结构化动作。它会经过参数校验，再进入对应核对页或处理器。20/20 静态契约检查证明当前动作均有解析和处理路径；25/25 业务测试进一步证明转账、AA、理财的关键状态变化正确。
