# 知银项目现状、团队分工与推进路线

> 更新日期：2026 年 9 月 28 日  
> 用途：供新成员快速了解项目当前状态、本人职责和后续比赛推进方式。

## 1. 项目当前处于什么阶段

知银已经不是只有界面效果的概念原型。目前项目具备可运行的手机沙箱、知银主应用、微信／支付宝／外卖等模拟应用、管家大模型、授权数据读取、账单和资金状态，以及部分能够真实改变沙箱数据的业务流程。

项目当前处于 **业务功能继续开发、跨模块联调、评测体系建设并行进行** 的阶段。公共底座已经搭好，但六项比赛功能的成熟度并不一致，因此暂时不能简单描述为“主体全部完成”或给出没有验收依据的总完成百分比。

判断某项功能是否完成，统一使用以下四级口径：

1. **界面原型**：页面可以展示和交互，但没有真实业务状态变化；
2. **单模块可用**：主要逻辑和数据已经实现，但尚未完成完整链路联调；
3. **业务闭环**：用户发起需求、Agent 规划、用户授权、系统执行、状态更新和结果反馈能够走通；
4. **验收通过**：正常、异常、歧义、撤销、重复操作和恢复等测试通过，并有可复现的评测证据。

目前项目整体可以概括为：**公共底座基本完成，部分重点场景已经形成业务闭环，六项功能仍需继续开发、合并和统一验收。**

## 2. 比赛的总体技术路线

知银的比赛方向，不是声称已经取得微信、支付宝或真实银行的正式合作权限，也不是为了演示效果伪造一套“看起来像真实接口”的流程。现实中的账单、余额、自动续费、联系人和支付权限受到平台合作、金融合规、用户隐私与账户安全等条件限制，学生团队很难在比赛开发周期内获得完整的生产级接入。

因此，本项目采用 **“沙箱提供数据与权限，Agent 完成理解、规划、执行和验证”** 的路线：

```text
用户自然语言需求
→ Agent 理解意图与补全必要参数
→ 读取沙箱授予的数据和权限
→ 生成可解释的执行方案
→ 风险检查与用户确认
→ 调用沙箱中的金融和跨 App 工具
→ 核对余额、账单、订单、订阅等最终状态
→ 向用户反馈结果或恢复建议
```

MobileGym 及其中的微信、支付宝、银行卡、外卖等模拟应用，承担三项基础职责：

- **提供数据来源**：向知银提供可控的余额、账单、订阅、联系人、订单和银行卡状态；
- **提供权限边界**：模拟用户在知银和第三方平台两侧授权、拒绝、撤销和限制权限；
- **提供执行环境**：让转账、扣费、取消续费、下单和支付等行为产生真实、可检查、可恢复的沙箱状态变化。

在这个架构中，沙箱不是参赛成果的终点，而是 Agent 的可控试验场。比赛重点是证明知银能够：

- 正确理解自然语言中的目标、对象、金额、时间和约束；
- 在信息不足或指令歧义时主动追问，而不是擅自执行；
- 跨越账单、订阅、银行卡、订单等不同数据源进行规划；
- 在高风险操作前进行风险检查并取得明确授权；
- 调用工具完成任务，并以最终业务状态而不是模型文字判断成功；
- 处理取消、修改、重复请求、执行失败和状态恢复；
- 给出有证据、可解释且不过度承诺的建议。

这也决定了当前的开发优先级：**先把 Agent 在沙箱中的端到端能力做完整、做稳定、做成可评测的结果，再逐步替换或扩展真实数据与真实联动。**

### 从沙箱走向真实接入

为了让后续真实接入不需要推翻现有 Agent，数据和执行能力应通过统一适配层提供。Agent 面向的是“读取账单”“查询余额”“取消订阅”“发起支付”等受约束工具，而不是直接依赖某个模拟页面的内部实现。

后续可以按可获得条件逐步推进：

1. **真实数据导入**：优先支持用户主动导出的账单文件、银行或支付平台账单，以及经过脱敏的测试数据；
2. **半真实联动**：接入公开接口、合作方测试环境或用户明确授权的第三方服务，用真实读取替换相应沙箱适配器；
3. **真实执行试点**：只有在具备正式授权、身份认证、风控、审计、幂等和合规条件后，才接入真实金融操作；
4. **保留沙箱评测**：即使未来获得真实接口，沙箱仍用于 Benchmark、异常注入、安全测试、演示重置和回归验证。

比赛展示时需要明确区分三件事：

- 已在沙箱内真实完成并产生状态变化的能力；
- 已设计好接口和权限边界、但尚未接入生产平台的能力；
- 未来需要平台合作与合规条件才能落地的真实金融能力。

这样的表述既能说明项目当前边界，也能证明方案具有向真实业务迁移的工程路径。

### 综合判断

- **进展靠前**：订阅管理、智能转账；
- **已有基础、仍需补齐和联调**：账单分析、卡片管理；
- **主要待推进**：理财业务闭环、完整跨场景任务链；
- **共同缺口**：六项功能尚未全部接入统一的可观测状态、自动判题和正式 Benchmark，因此“页面能操作”不能直接等同于“比赛功能验收完成”。

## 4. 现有工程基础

目前已经具备的公共能力包括：

- 可交互的 MobileGym 手机沙箱，可从手机桌面进入知银、微信、支付宝、外卖等应用；
- 知银经典模式和 AI 原生模式，以及可切换的私人管家；
- 服务端代理的大模型对话，支持结构化动作和用户确认边界；
- 微信支付、支付宝、银行卡、订单、账单、订阅等沙箱数据；
- 平台双方授权、权限范围和撤销流程的模拟；
- 长期事实记忆和用户画像的基础能力；
- 沙箱控制台，可重置部分状态、配置模型并辅助测试；
- 已有单元测试、组件测试和部分端到端冒烟测试。

这些能力让后续工作可以直接围绕“业务是否真的完成、是否稳定、是否能够被证明”展开，而不需要重新搭建演示框架。

## 5. 三位成员的建议分工

### 成员 A：场景 1、5、6 的业务开发

负责智能转账、订阅管理和跨场景联动的产品逻辑、功能实现、数据闭环和本模块 Bug 修复，同时向评测负责人提供：

- 预期行为与业务规则；
- 可测试入口和测试数据；
- 关键状态变化；
- 已知限制和安全边界；
- 可用于答辩的真实案例与实现说明。

### 成员 B：场景 2、3、4 的业务开发

负责账单分析、理财操作和卡片管理的产品逻辑、功能实现、数据闭环和本模块 Bug 修复，并提供与成员 A 相同格式的测试和材料输入。

### 新成员：评测、测试与技术交付

新成员最适合承担的不是再认领一个孤立页面，而是贯穿六项功能的 **Agent 评测、质量保障和技术交付**。这项工作与两位开发成员同步开始，不需要等全部功能完成后再介入。

她的主要职责是：

1. **建立六项功能状态表**  
   按“界面原型、单模块可用、业务闭环、验收通过”记录真实进度，不把页面展示当作功能完成。

2. **持续进行功能验收**  
   对已可用流程覆盖正常操作、参数歧义、多轮修改、取消、拒绝授权、重复点击、刷新恢复、余额不足、网络失败等情况，记录复现步骤并跟进复测。

3. **建设 Agent Benchmark**  
   将自然语言任务整理为可重复测试的用例，为每条任务定义初始状态、用户指令、允许操作、预期最终状态和失败条件。判定重点是余额、流水、订阅、订单等实际状态，而不是模型是否说“已经完成”。

4. **开展安全和异常测试**  
   重点测试绕过确认、重复扣款、越权读取、恶意页面文本、提示词注入、任务中断、回执丢失和状态恢复。发现业务逻辑问题后交给对应模块负责人修复，由她完成复测。

5. **整理技术与比赛交付材料**  
   持续沉淀系统架构、功能流程、接口与状态、测试结果、安全边界、部署方式和已知限制；后期负责统一整理答辩 PPT、演示脚本、问题库和比赛版本检查单。材料内容由三个人共同提供，她负责统一和验证，不能脱离实现凭空编写。

## 6. 新成员可以立即开始的工作

### 第一阶段：熟悉项目并建立基线

- 在自己的环境中独立克隆、安装、启动手机沙箱；
- 跑通知银、微信支付、支付宝和外卖的主要入口；
- 建立六项功能状态表；
- 记录首次体验中的启动问题、交互问题和明显 Bug；
- 验证数据重置后能否重复演示。

### 第二阶段：从成熟功能开始验收

优先测试订阅管理和智能转账，因为这两项已经具备较完整的数据闭环。建议第一批准备 20～30 条有意义的测试，包括：

- 同一需求的不同自然语言表达；
- 缺少金额、时间、对象等必要参数；
- 修改已经生成的方案；
- 拒绝授权或中途取消；
- 重复点击和重复发送请求；
- 余额不足、超过限额、银行卡挂失；
- 页面刷新、服务重启和回执丢失；
- 模型声称完成但系统实际未执行。

每条问题至少记录：初始状态、操作步骤、预期结果、实际结果、截图或日志、严重程度、负责人、修复版本和复测结果。

### 第三阶段：形成自动化评测

当某一流程稳定后，再把人工用例转为自动化任务。每条任务至少应验证：

- 意图和关键参数是否正确；
- 高风险操作是否经过明确确认；
- 系统是否只执行被授权的动作；
- 最终业务状态是否正确；
- 是否出现额外副作用；
- 失败后是否可解释、可恢复；
- 重复请求是否保持幂等。

后续可统计任务成功率、参数正确率、虚假完成率、越权率、重复扣款率、平均步骤数和恢复成功率。指标必须来自可复现任务，不能用主观印象填写。

### 第四阶段：比赛交付

- 完成六项功能的最终验收报告；
- 输出 Benchmark 和安全测试报告；
- 整理部署说明、启动脚本和故障恢复手册；
- 冻结比赛演示版本和演示数据；
- 准备短版、标准版和完整版演示流程；
- 准备离线录屏和快速重置方案；
- 根据真实实现和测试数据制作答辩材料。

## 7. 团队协作方式

- 两位业务开发成员继续实现和修复各自负责的场景；
- 新成员持续验收已经可测试的部分，并把问题分配给对应负责人；
- 业务规则不明确时，由场景负责人给出预期行为，评测负责人不自行猜测；
- 每完成一个稳定流程，就同步补充测试、状态判定和材料，不把所有评测工作留到最后；
- 跨模块问题由三人共同定位：业务 Bug 由场景负责人修复，评测框架、判题、部署和交付问题由新成员负责；
- 主分支只合入经过基本构建和测试的版本，重要演示节点创建明确版本标签。

## 8. 近期共同目标

近期目标不是继续堆积孤立页面，而是完成三个结果：

1. **补齐六项功能中的主要业务缺口**，尤其是理财闭环和完整跨场景任务链；
2. **把已有功能统一接入可验证的状态与判题体系**，证明 Agent 真实执行，而不是只生成一段像成功的回复；
3. **形成一次完整的“发现问题—开发修复—重新验证”循环**，让测试、开发和材料沉淀成为持续流程。

最终参赛作品需要同时满足：功能能跑、状态可信、风险可控、过程可解释、环境可部署、演示可恢复、效果有数据证明。
