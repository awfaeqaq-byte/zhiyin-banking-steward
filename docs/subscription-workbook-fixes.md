# 订阅管理手测失败修复

本文件保留早期订阅专项修复记录。2026年10月22日的V2六模块修复与47条问题复测见[最新执行报告](testing/v2/执行报告.md)，两个测试范围分别统计。

依据2026-10-15逐条测试记录中的6条“失败”实施；保留原始测试结果，不将自动回归代替手测复测。5条“阻塞”仍表示相关手测条件未满足。

| 编号 | 修复行为 | 自动回归 |
| --- | --- | --- |
| S01 | 沿用上一提交的有效授权检查；未授权不复用历史清单，纯清单查询不请求模型 | 未连接、旧聊天、拒绝/断开、模型429桩 |
| S02 | 两边即当前两平台，完整列出有效项目；按平台及周期计算项数、合计，保留同名两项，未知日期不猜 | 微信6项、支付宝5项108元、同名18/28元、年费与未知日期 |
| S08 | 同类组“稍后再说”确定路由到订阅事项，明确暂缓一天；多组不明时追问 | 当前组合ID、later偏好、到期恢复、提醒与签约不变 |
| S09 | 取消只准备当前真实项目；对话核对组件仅显示该对象，目标在第6项也可核对 | 精确平台/ID/金额、目标入口点击前不调用取消回调 |
| S12 | 同名对象先列真实平台和金额，后续选择和改口沿用同一任务；不匹配则追问 | 微信18元切到支付宝28元、错误金额拒绝、真实持久消息链 |
| S19 | 用识别器同一组过滤规则产生未识别原因，引用本轮实际历史样本，不限于本月；不让模型补造往月交易 | 两期不足、同月多笔、18/18/22波动、旧聊天虚假7月样本 |

取消最终仍经原有核对面板和合作方确认；准备方案、点击打开核对、聊天里的“确认”均不代表平台已经取消。只关提醒、展示动作标记等请求不能误生成取消方案。

复测时使用独立沙箱测试数据，按原表6条失败操作顺序核对：宁宁回复、知银界面、合作方签约状态。S12改口后只应留下最新目标的可操作入口；S19核对实际交易日期、数量和金额，不用模型措辞当作账单证据。原有阻塞变体仍需单独准备受控日期、撤权、迟到快照、取消故障或有效注入条件。
