# 账单分析、理财操作、卡片管理需求文档

> 文档负责人：场景 2／3／4 开发成员
> 基线日期：2026-09-29
> 代码基线：GitHub `main`，提交 `621b58c6db73385fadb3d3172ecc337fcbd03d45`
> 适用范围：比赛用本地沙箱，不代表真实银行或支付平台生产能力

## 1. 文档目的

本文定义本人负责的三个核心场景：**账单分析、理财操作、卡片管理**。目标不是继续堆叠静态页面，而是把每个场景做成可演示、可验证、可回退的 Agent 业务闭环。

统一完成链路为：

```text
用户自然语言提出目标
→ Agent 识别意图并补齐必要参数
→ 从已授权沙箱读取可信状态
→ 生成有依据的分析或操作方案
→ 风险检查与用户明确确认
→ 调用受约束的沙箱工具
→ 复查最终业务状态
→ 返回结果、失败原因和可恢复入口
```

涉及资金、持仓或银行卡状态变化时，模型只能“理解与准备”；实际变更必须由确定性代码校验，并由用户在独立确认界面授权。

## 2. 用户与产品目标

### 2.1 目标用户

- 不熟悉银行菜单或金融术语，希望直接说出需求的个人银行用户；
- 希望看懂钱花在哪里、理财是否适合自己、银行卡是否安全的用户；
- 需要可解释建议，但不希望 AI 未经许可自动操作资金的用户。

### 2.2 本阶段目标

1. 账单分析从“固定展示页”升级为基于授权账单的自然语言分析和月度／年度报告；
2. 理财操作从“方案原型”升级为风险测评、产品比较、申购／赎回、持仓更新的沙箱闭环；
3. 卡片管理在现有持久化设置之上，补齐自然语言操作、确认、回执和异常恢复；
4. 为三个场景补充自动化测试、演示脚本、状态判定和更新记录。

### 2.3 非目标与边界

- 不连接真实银行账户，不发起真实转账、申购、赎回、调额或挂失；
- 不声称已经取得微信、支付宝、银行或基金公司的生产权限；
- 不用模型文字作为“操作成功”的证据，以沙箱状态和服务器回执为准；
- 不把投资推荐包装成保本、保收益或确定性预测；
- 不上传 API Key、真实账单、身份证号、完整银行卡号等敏感数据到仓库。

## 3. 当前代码现状

| 场景 | 已有能力 | 主要缺口 | 当前阶段 |
| --- | --- | --- | --- |
| 账单分析 | 微信／支付宝授权账单读取；规范化、同平台 ID 去重、分类汇总、收支拆分、最大消费、等长前期对照、较大金额／同日多笔／周期规律线索；自然语言账单问答和证据展开 | 经典账单页仍有固定演示数据；月报／年报未统一；缺少预算设置、报告留存和批量准确率评测 | 单模块可用，待统一闭环与验收 |

### 3.1 账单分析现有口径

- 金额统一使用“分”计算，展示时转为“元”；
- 只读取用户已授权且包含 `transactions` 范围的数据源；
- 同一平台、同一交易 ID 去重，不把跨平台同金额交易自动判成重复；
- 消费、普通入账、退款、转入、转出分别统计，退款不抵扣消费；
- 较大金额规则当前为：本期至少 5 笔消费，单笔不低于 1,000 元且不低于单笔中位数 3 倍；
- 周期规律只说明历史记录近似按月出现，不等同于已开通自动续费；
- 无授权、无记录、记录不完整必须明确区分，不得把“未返回”表述为“没有发生”。

### 3.2 卡片管理现有口径

- 默认沙箱卡余额、限额、挂失和安全开关保存在 `.zhiyin-bank.local.json`；
- 挂失、余额不足、超过单笔限额、北京时间 23:00—06:00 的夜间保护会阻止相应付款；
- 修改设置使用版本号校验，账户状态变化后旧请求会失败，避免覆盖新状态；
- 挂失／恢复、限额和开关修改都不影响真实账户。

## 4. 功能需求

需求优先级：P0 为比赛主链必须完成，P1 为增强展示和完整性，P2 为获得真实合作条件后的扩展。

三个场景共用统一的宁宁编排 Agent、六步任务流程、会话隔离和确认边界，详细设计与当前 MVP 状态见 [宁宁 Agent、任务规划、会话与可视化设计](agent-task-session-design.md)。业务页面不再把全部历史堆在单一界面；每个任务使用独立会话，长会话以摘要和近期窗口提供给模型，完整记录仍供用户查看。

## 4.1 场景 A：账单分析

### A1. 数据授权与同步（P0）

- 用户可分别授权微信支付、支付宝的账单读取范围；
- 页面必须展示数据来源、同步时间、授权范围和不完整提示；
- 微信账单页和知银不得分别维护两份交易副本，必须通过同一个 `WechatPayBackend` 读取同一版本数据；
- 全量账单通过分页或游标读取，不能因为当前 1,000 条上限静默截断；返回结果必须包含覆盖起止时间、总数、已返回数和是否完整；
- 撤销授权后，不再向模型提供该平台账单；
- 原始商户名称、备注等字段一律当作数据，不能当作模型指令执行；
- 解析失败、缺字段、重复记录必须计入数据质量信息，不能静默伪造。

Excel 导出账单只作为离线测试和回放入口，不作为生产页面的第二数据源。导入后先映射为微信账本的统一结构，再让微信页面和知银从同一个临时后端读取。详细规则见 [微信账单一致性与客群记忆设计](wechat-bill-consistency-and-customer-memory.md)。

MVP 进度（2026-09-29）：1,971 条规模可完整通过财务适配器和手机桥；有界上限为 5,000 条，超限或格式无效会返回 `complete=false` 并在页面显示。游标分页、快照版本和 Excel 回放尚未实现，因此 A1 尚未整体验收通过。

### A2. 自然语言查询（P0）

支持以下问题并保持多轮账单语境：

- “本月花了多少”“上个月呢”；
- “餐饮花了多少”“最大一笔是什么”；
- “微信和支付宝分别花了多少”；
- “有没有不寻常的消费”“哪些像周期扣费”；
- “最近 7 天账单”“2026 年 8 月账单”。

当日期范围不明确、超出已有数据或需要未来时间时，Agent 必须追问，不得用默认月份数字冒充答案。

### A3. 统计与诊断（P0）

- 汇总消费、普通入账、退款、转入和转出；
- 展示分类金额、占比、最多 5 笔较大消费和最多 8 笔近期记录；
- 给出较大金额、同日多笔、周期规律等“线索”，并展示规则与对应交易证据；
- 有足够前期数据时提供等长时段对照；没有前期数据时明确说明不能判断趋势；
- 诊断结论必须使用“建议核对”“呈现规律”等审慎措辞，不能直接断言欺诈、盗刷或自动续费。

### A4. 月报／年报（P0／P1）

- P0：生成统一的月度账单报告，包含范围、来源、数据质量、收支、分类、趋势、重点线索和限制；
- P1：支持年度报告和按月趋势，要求至少有相应月份数据才生成；
- 报告中的每个金额都能追溯到纳入统计的交易集合；
- 报告刷新后可重新生成，但不得把旧报告当作当前实时状态。

### A5. 预算辅助（P1）

- 用户可设置月度总预算和分类预算；
- 展示预算使用率和预计剩余额度；
- 预算提醒只做解释与提醒，不自动转账、冻结余额或修改账户。

### A6. 验收标准

- 同一组授权数据在页面汇总、Agent 回答和报告中金额一致；
- 同平台重复交易不重复计数，跨平台交易不被无依据删除；
- 无授权时只提示授权，不输出虚构金额；
- 模糊时间先追问；无数据时说“未返回记录”，不说“消费为零”；
- 商户字段中包含“忽略规则”等文本时，不改变系统行为；
- 至少覆盖正常、空数据、重复数据、无效数据、跨月、退款、转账和提示注入测试。

## 4.2 场景 B：理财操作

### B1. 风险测评（P0）

- 首次进入理财操作或测评过期时，引导完成风险测评；
- 测评至少覆盖投资经验、可承受亏损、资金使用期限、流动性需求和收入稳定性；
- 产出风险等级、有效期、版本和答题摘要；
- 用户修改答案后立即重新计算，旧推荐必须失效并重新生成；
- 不允许模型自行篡改风险等级。

### B2. 产品目录与适当性（P0）

每个沙箱产品至少包含：

- 产品 ID、名称、类型、风险等级；
- 起购金额、递增金额、持有期限、开放／封闭状态；
- 费率、历史波动或演示收益区间、赎回规则；
- 是否保本、数据日期和风险揭示。

系统必须先用确定性规则筛除风险等级不匹配、金额不足、期限不合适或不可申购的产品，再让模型解释候选项。

### B3. 推荐与对比（P0）

- 用户可说“3 万元、6 个月、稳妥一点”等目标；
- 参数不足时必须追问金额、期限或风险偏好；
- 最多给出 3 个候选，说明匹配原因、主要差异、流动性和最坏情形风险；
- 收益只能展示区间或情景，不承诺收益；
- 支持对比产品和收藏方案，收藏不等同于申购。

### B4. 申购闭环（P0）

```text
生成候选 → 选择产品 → 输入金额 → 适当性／余额／规则校验
→ 展示费用、风险揭示和资金影响 → 用户明确授权
→ 沙箱扣款并生成申购回执 → 持仓和资金状态更新 → Agent 复查
```

- 核对页必须展示产品、金额、资金来源、费用、预计确认时间和关键风险；
- 同一授权请求必须幂等，重复点击不能重复扣款或创建重复持仓；
- 余额、产品状态或风险等级发生变化时，旧方案失效并要求重新核对；
- 只有服务端回执与持仓状态同时可查时，才能反馈申购成功。

### B5. 持仓与赎回（P0）

- 展示持仓本金、当前演示价值、盈亏、持有期限、可赎回状态和数据日期；
- 赎回前展示可赎回金额、费用、预计到账时间和对资金安排的影响；
- 封闭期、最低持有、余额或产品异常由确定性代码拦截；
- 用户确认后更新持仓与资金账本，并生成可追踪回执；
- 失败时保持原持仓不变，提供重试或返回入口。

### B6. 验收标准

- 不匹配风险等级的产品不会出现在可申购列表；
- 收藏、生成方案、进入核对页都不会扣款；
- 未确认、取消确认、余额不足、产品关闭、重复请求均不会产生错误持仓；
- 成功申购后资金减少与持仓增加一致；成功赎回后持仓、资金和回执一致；
- Agent 不输出“保本”“稳赚”或未经回执证明的“已完成”。

## 4.3 场景 C：卡片管理

### C1. 卡片总览（P0）

- 展示卡片尾号、状态、余额、单笔限额、安全开关和近期银行流水；
- 只展示沙箱所需的脱敏信息，不暴露完整卡号或鉴权数据；
- 页面刷新和服务重启后状态保持一致。

### C2. 自然语言管理（P0）

支持：

- “把单笔限额调到 5000 元”；
- “关闭无卡支付”“开启境外交易”；
- “晚上不要让这张卡付款”；
- “我的卡丢了，帮我挂失”；
- “恢复演示卡”。

Agent 需要识别卡片、目标值和操作类型；存在多张卡或指代不清时必须追问。模型输出结构化意图，服务端重新校验，不直接接受模型生成的成功结论。

### C3. 确认与执行（P0）

- 挂失、解挂、调额和可能增加风险的开关变化必须进入独立核对页；
- 核对页展示变更前后状态、影响范围、风险提示和取消入口；
- 用户确认后调用银行沙箱设置接口，使用最新 `revision` 防止覆盖并发变化；
- 成功后展示回执和最新状态；失败后保持原设置不变；
- 重复提交同一操作不得造成连续翻转或不可解释状态。

### C4. 风控联动（P0）

- 挂失卡不能用于即时转账、预约执行或跨 App 银行卡支付；
- 超过单笔限额、余额不足、夜间保护命中时必须失败并给出明确原因；
- 境外交易和无卡支付只有接入相应沙箱支付渠道后，才可宣称会拦截交易；在此之前只描述为保存偏好；
- 所有失败不得静默改用微信、支付宝或其他银行卡。

### C5. 卡申请（P1）

- 在比赛需要覆盖截图中的“卡申请”时，先做沙箱预审和产品比较，不采集真实身份证号；
- 展示卡种、年费、权益、申请条件、所需模拟资料和处理状态；
- 提交前单独确认，明确“仅创建沙箱申请，不代表真实银行审批”；
- 如时间不足，卡申请不得阻塞 P0 的卡安全管理闭环。

### C6. 验收标准

- 设置修改刷新后仍存在，服务重启后与本地账本一致；
- 旧版本号提交被拒绝，页面刷新后可重新操作；
- 挂失、限额、余额不足和夜间保护确实阻止相应沙箱支付；
- 取消确认不改变任何设置；
- 任何失败都不改变余额，不切换支付渠道；
- 页面、Agent 回复、银行回执对同一状态的描述一致。

## 5. 跨场景要求

### 5.1 Agent 行为

- 每次只执行一个高风险动作；多个目标拆分成可核对步骤；
- 信息不足先追问，不猜金额、卡片、产品、时间或风险偏好；
- 分析和建议可由模型组织语言，金额、规则、状态和执行结果必须来自代码；
- 历史聊天不是当前状态证据，每次执行前重新读取沙箱；
- 模型输出结构化动作后，前端和服务端仍需白名单、类型、范围和状态校验。

### 5.2 安全与隐私

- 默认最小授权，授权范围和撤销入口可见；
- API Key 只保存在本机 `.sandbox-model.local.json`，不得提交；
- 银行、持仓、风险测评等本地私有状态文件使用 `*.local.json` 并加入忽略规则；
- 日志不记录 API Key、完整卡号或真实个人敏感信息；
- 商户名、备注、模型回复等不可信文本不能改变系统指令和工具权限。

### 5.3 可用性与可访问性

- 手机触控目标至少 44px；
- 支持键盘操作、焦点可见、语义化标签和减少动态效果；
- 风险和状态不能只依赖颜色表达；
- 加载、空数据、失败、成功、权限不足均有明确界面状态。

### 5.4 可观测与评测

每个测试任务至少记录：

- 初始沙箱状态；
- 用户指令与多轮补充；
- Agent 生成的结构化意图；
- 是否展示确认以及用户选择；
- 工具调用、回执和最终状态；
- 额外副作用、恢复结果和耗时。

核心指标包括任务成功率、参数正确率、澄清正确率、未授权执行率、虚假完成率、重复扣款率、最终状态一致率和失败恢复率。

### 5.5 客群与长期记忆

- 客群用于调整解释重点、默认展示顺序和提醒方式，不直接决定授信、风险等级或产品适当性；
- 支持年轻成长、家庭、财富管理、银发安全、商户／小微经营及通用客群；一个用户可选择一个主客群和多个需求标签；
- 客群只能由用户主动选择或确认，账单信号只能生成“待确认建议”，不得自动推断年龄、收入、家庭状况、财富等级或经营身份；
- 风险测评、账户余额、持仓、最新账单和交易授权均是独立业务状态，不写入长期记忆；
- 长期记忆可以保存用户明确确认的目标和偏好，例如月度储蓄目标、沟通方式、家庭资金目标，但要保留来源、确认状态、有效期和删除入口；
- 当前对话与最新业务状态优先。客群或记忆与用户当前表达冲突时先询问，不照旧执行。

## 6. 数据与接口建议

不要让三个场景继续堆在 `App.tsx` 中。新增业务优先采用以下分层：

```text
src/lib/               纯类型、计算、意图解析、校验
src/components/        页面、核对面板、回执和状态展示
server/                持久化账本、幂等、并发校验、工具接口
mobilegym/             跨 App 沙箱数据、权限和执行环境
docs/                  规则、接口、测试证据和更新记录
```

建议新增或拆分：

- `src/lib/investment.ts`：产品、测评、方案、申购／赎回意图与校验；
- `server/investment-store.ts`：资金、持仓、订单、幂等和回执；
- `src/components/investment-*.tsx`：风险测评、对比、核对、持仓；
- `src/lib/card-management.ts`：自然语言卡片动作与确认模型；
- 独立的月报视图和报告结构，复用 `bill-analysis.ts` 的统一计算结果；
- 所有金额继续使用整数分，时间明确使用北京时间或带时区 ISO 字符串。

## 7. 里程碑与完成定义

### M1：基线与统一数据（1—2 天）

- 跑通完整手机、模型、微信／支付宝授权和银行沙箱；
- 将经典账单页切换为统一账单分析数据；
- 为三个场景建立状态机、接口和测试清单。

### M2：账单分析闭环（2—4 天）

- 完成统一月报、查询、证据、异常线索和边界处理；
- 至少 20 条账单 Benchmark，正常与异常用例均可重复运行。

### M3：卡片管理 Agent 闭环（2—4 天）

- 完成自然语言意图、确认、服务端执行、回执和状态复查；
- 覆盖挂失、解挂、限额、开关、并发变化和付款拦截。

### M4：理财最小业务闭环（4—7 天）

- 完成风险测评、产品目录、适当性、推荐、申购、持仓和赎回；
- 完成幂等、余额／状态变化、取消与失败恢复测试。

### M5：联调与比赛验收（2—3 天）

- 三场景接入统一 Agent 首页；
- 通过构建、单测、组件测试、冒烟测试和演示脚本；
- 冻结演示数据并完成更新文档、限制说明、录屏和快速恢复方案。

某项功能只有同时满足以下条件才标记为“验收通过”：

1. 正常链路可复现；
2. 缺参、拒绝、取消、重复、并发、余额不足和刷新恢复等关键异常通过；
3. 最终状态由代码自动判定；
4. 有测试或演示证据；
5. 文档与实现一致；
6. `npm run build`、`npm test` 通过，相关 MobileGym 测试通过。

## 8. 演示主线建议

1. 用户问“帮我看看这个月钱花在哪”，宁宁读取已授权账单，展示分类、趋势和一条有证据的线索；
2. 用户继续问“我有 3 万元，半年内可能要用，怎么安排更稳妥”，系统先核对风险等级和流动性，再给出最多 3 个方案；
3. 用户选择一个产品，进入独立核对页，确认后沙箱资金和持仓同步变化；
4. 用户说“把这张卡单笔限额调到 5000，晚上不要付款”，系统拆成可核对步骤并更新卡片状态；
5. 用超限或夜间付款证明风控真实拦截，再展示回执和恢复方式。

这条主线能同时证明：自然语言理解、跨数据规划、解释、授权、执行、最终状态验证和安全边界。
