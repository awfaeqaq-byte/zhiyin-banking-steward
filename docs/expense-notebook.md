# 随手记消费

在 AI 原生模式的管家首页点“随手记消费”，或发送“今晚和李娜、小王吃饭，我先付，最后一起算”。选择并授权微信群、确认活动参与人后开始；默认由本人垫付。之后直接在原有输入框逐笔说消费，点活动摘要查看记录，展开单笔依据核对分摊金额。发送“最后一起算”进入核对，选中本批记录，确认后发起沙箱微信群收款。发起成功表示等待成员付款，不代表到账。这里记录已垫付消费，不会再次扣款。

## 五条试用语句

先选本人、李娜、小王三人；每轮只发送一笔或一个操作。

1. `卤味42`
2. `蚂蚁上树28`
3. `饮料10，李娜3元，剩下我和小王平分`
4. `又买了饮料16`，收到保存反馈后下一轮发送 `刚才饮料改成18`
5. `烧烤236，小王没吃`

以上已通过真实模型序列验证：总额 334 元，本人 150.83 元、李娜 150.34 元、小王 32.83 元，应收 183.17 元。首批发布后再次新增饮料会进入下一批，刷新能恢复记录。混合句“饮料16，最后一起算”先保存再展开结算；无法解析时明确提示未保存，不把自然语言答复当作落盘凭据。

## 持久化与防重

- `src/components/expense-notebook.tsx` 由 `steward-chat-home.tsx` 接入；`expense-service.ts` 调用真实本地 API `GET/POST /api/zhiyin/expenses`，服务端实现为 `server/expense-store.ts`。
- 浏览器在 localStorage 保存随机 `zhiyin-expense-scope` 和当前活动 ID，账本保存在服务目录的 `.zhiyin-expenses-<scope>.local.json`。scope 通过请求头传递以隔离沙箱记录；清除浏览器标识后不会自动找回旧 scope。此机制不是生产身份认证。
- 金额使用整数分，固定金额先分配，余款按权重分摊。服务端校验成员、金额与版本；文件锁、临时文件原子替换和请求 ID 处理并发及重复请求，客户端网络重试复用同一请求 ID。
- 发布前先持久化结算批次并锁定消费，再以该批次 ID 发布。回执丢失时保留锁定，可核对微信记录恢复状态或以原批次继续确认；只有核对未发布后才恢复修改，避免另建一笔重复收款。

## 边界与交接

只支持收回本人垫付的费用；他人垫付可以记录，但含这类消费的结算会被阻止。每轮一个操作；单次结算最多 20 个分摊子项目（不等同于 20 笔消费），超出时分批选择。界面日期按本地设备日期显示。当前微信链路是沙箱，并非真实微信或生产认证系统。

验证记录：317 项测试通过、生产构建通过；此前针对新增功能测得行覆盖率约 92%、分支约 84%、函数约 86%，不是全项目覆盖率。浏览器验证脚本为 `scripts/expense-notebook-smoke.mjs`，截图为 `.impeccable/review/expenses-mobile.png` 和 `expenses-desktop.png`。脚本依赖本地 3000 端口演示服务、可用模型服务、Chrome 与 `mobilegym` 的 Puppeteer；会在独立沙箱中创建记录，不能当成纯只读检查。
