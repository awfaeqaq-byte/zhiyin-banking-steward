# 大额与重复转账核对

2026-10-19。此功能覆盖知银银行沙箱的即时转账和单次预约；没有替代微信／支付宝钱包、商家订单付款或真实银行风控。

## 用户确认的规则

- 单笔金额达到 5000 元时展示大额提醒。
- 同一付款账户、同一事项、同一收款人，在最近 10 分钟内已有相同或相近金额记录时，展示可能重复转账。
- 相近：与历史金额差值不超过该历史金额的 1%，且最多差 100 元；以整数分计算，边界包含在内。
- 当前“同一事项”按稳定的 `workspaceId` 精确匹配，不根据标题、姓名或模型文字推测。无事项的手工入口只和其他无事项记录比较；不同 workspaceId（包括同场景内关联的不同子任务）不会自动合并。未实现跨任务语义相似度检测。
- 成功转账使用实际完成时间；已授权且仍待执行的预约使用创建时间，并同时展示计划执行时间。失败、取消、过期窗口及未来记录不作为本次匹配依据。
- 不设置小额豁免：重复识别与大额提醒分别计算，100 元也可能触发重复提醒。

## 用户流程

原对话整理方案 → 现有转账核对页 → 服务端返回大额／重复证据 → 用户核对原记录（对象、金额、状态、时间与编号） → 勾选仍需新转账 → 点击原来的最终确认按钮。

不增加任务管理页，不要求用户输入技术分类。复核勾选本身不付款。未勾选时确认按钮禁用；返回修改或收到另一份草案时清除勾选。原方案失效后须重新准备，不能沿用旧勾选。

## 服务端保护

`prepare` 从银行账本计算风险，忽略客户端伪造的 review 字段。需要提醒时为当前草案签发随机 token，连同证据保存在本地账本中。`confirm`／`schedule` 除原 `authorized:true` 外还需匹配的 `riskReviewToken`；服务端在执行前重新检查风险。令牌不能跨草案使用，也不免除余额、限额、挂失、夜间保护、预算预留、过期和 revision 校验。

同一草案重复提交仍先返回原回执／原预约，不新增付款。此功能解决“另一笔新请求可能重复”，原有请求幂等解决“同一笔网络重试”，两者分开。

旧草案没有风险证据时，如果现在触发规则，服务器拒绝直接执行，用户返回修改后重新核对。没有新提醒的普通小额转账保持原流程。

## 预约到期

授权预约时记录用户已核对的历史记录 ID。到期只检查实际成功转账，不把仍未付款的预约当成到账：若同事项出现未在当时证据中核对过的新重复／相近付款，该预约标记失败并保留原因，不扣第二笔款。用户到原记录核对后重新安排。

如果用户创建第二个预约时已经明确核对并接受第一笔预约，后续第一笔按计划完成不会再拦截这个有意安排。预约创建前已核对的大额不在到期时要求用户再次在线勾选。

## 实现位置

- `src/lib/transfer-risk.ts`：规则、证据和持久化校验。
- `server/transfer-risk.ts`：草案风险确认门禁。
- `server/bank-store.ts`、`server/smart-bank.ts`：准备、即时确认、预约授权与到期检查。
- `src/components/transfer-risk-review.tsx`、`bank-transfer.tsx/css`：核对证据及复核勾选。
- `scripts/transfer-risk-smoke.mjs`：独立临时银行账本、真实 API 和真实产品组件的浏览器测试，不访问私人账本或模型凭证。

## 验收范围

覆盖相同／相近金额、1%与100元上限、10分钟边界、不同对象／事项、无事项入口、取消及失败预约、伪造令牌、跨草案复用、旧版本、重启恢复、HTTP授权、重复提交和预约到期新增付款；组件覆盖大额／重复／待执行记录及展开证据。

本轮当前工作区全量回归为 156 个文件、974 项测试通过；随后补充两项组件测试，最终专项 23 项通过。三个新增规则／门禁／展示模块的行覆盖率为 100%，分支覆盖率为 95.74%（不是全项目覆盖率）。TypeScript 与生产构建通过。隔离浏览器验证了 390 像素和宽屏布局、未核对时禁用、勾选不扣款、最终确认只新增一笔，以及无页面脚本错误。

本机沙箱保护不等于真实支付平台反欺诈或身份认证，不能作为跨账户、跨平台的重复付款全面检测。依赖未变更；本轮 npm audit 仍有既有告警，未在本功能中升级依赖。
