# 微信账单一致性与客群长期记忆设计

> 更新日期：2026-09-29  
> 状态：MVP 已实现（覆盖完整性 + 本机 Excel 自动回放 + 客群服务偏好），分页快照待续  
> 适用范围：MobileGym 微信支付沙箱、知银账单分析、离线 Excel 测试回放、用户确认的客群资料

## 1. 目标

本设计解决两个问题：

1. 微信页面显示的账单和知银分析必须来自同一个权威数据源，并能证明数量、金额、分类和覆盖时间一致；
2. 知银可以按用户主动确认的客群和金融需求调整服务重点，同时避免从账单偷偷推断年龄、收入、家庭、财富等级、经营身份或风险承受能力。

核心原则：

```text
一个权威账本
→ 一个规范化口径
→ 微信页面与知银分别按授权读取
→ 同一快照版本可对账
→ Excel 只做离线测试回放，不成为第二套生产数据
```

### 2.3 主要处理

- 原始日期是 Excel 1900 日期系统的数字序列，不是损坏文本；导入器按 `1899-12-30` 纪元还原，不能再用字符串正则误判；
- 1,971 条金额都可精确转换为整数分；汇总由明细重算，不信任工作簿顶部的展示文字；
- 1,971 个交易单号全部唯一，但进入浏览器前仍转换为稳定哈希 ID，避免暴露原生标识；
- 78 条 `收/支=/` 的中性记录当前进入隔离统计，不强行算作支出或收入；其余 1,893 条进入统一微信账本；
- 商户、商品、状态和备注始终按不可信文本处理；原始文件不修改、不复制进仓库；
- 知银读取上限已提高到 5,000，因此 1,893 条已导入记录不会静默截断。

### 2.4 使用结论

这份文件定义为 `golden-private-fixture`：

- 日期修复文件不参与配置、导入、测试或对账，保留在输出目录仅供人工追溯。

## 3. 当前工程现状

项目已经具备正确的基础方向：

- 微信支付页面通过 `WechatPayBackend` 读取账本；
- 知银的 `finance-access.ts` 也通过 `getWechatPayBackend()` 读取微信历史；
- 知银发起 `transactions` 授权后，MobileGym 才把微信数据通过同源手机桥传入；
- 金额在微信账本和知银内部都使用整数分；
- 商户等文本进入模型前被当作数据，不作为指令。

已在 MVP 修复：

- 知银与手机桥的交易上限由 1,000 提高为 5,000；
- `FinancialSourceSnapshot` 新增 `transactionCoverage` (`total` / `returned` / `invalid` / `complete` / `from` / `to`)；
- 超限或存在无效记录时，连接页显示“数据不完整”，账单 Agent 只能把结果解释为已返回小计；
- 微信退款映射为 `refund`，不再默认当作普通收入；
- “我的服务偏好”支持主客群、10 类需求标签、三场景功能预览和用户显式保存；关闭后不进入模型上下文。
- 本机 Excel 回放支持启动时自动读取、日期序列解析、金额转分、原生 ID 哈希、分类映射、隔离统计和 SHA-256 锁定；页面实测可打开 9 月明细并得到 ¥12,020.89 支出、¥7,596.31 入账。

仍需修复的差异风险：

1. 5,000 条是 MVP 有界传输，还没有游标、快照版本和断点续传；
2. 微信账本仅有 `expense`／`income`，没有中性交易模型；
3. 知银规范结构缺少支付方式、交易状态、商户订单号和退款关联；
4. 微信页面的月汇总和知银分析仍缺自动控制量对账；
5. Excel 回放当前是本机开发能力，生产微信授权接入仍需正式数据接口、游标和快照版本。

## 4. 单一数据源架构

### 4.1 运行时数据流

```text
微信支付账本存储／WechatPayBackend
        ├─ 微信账单页面：按月、分类、搜索读取
        └─ 知银授权适配器：按范围、分页、快照版本读取
                ↓
        统一规范化交易 NormalizedTransaction
                ↓
        账单分析、报告、订阅识别、异常线索
```

禁止：

- 微信页面使用 JSON A，而知银使用手写 JSON B；
- 为了演示在知银侧复制一份固定账单；
- 让模型自己解析 Excel 或自己算金额；
- 数据被截断后仍显示“完整年度账单”。

### 4.2 Excel 回放数据流

```text
本机 Excel
→ 受控解析器
→ 字段校验、金额转分、日期解析、文本转义
→ 有效记录 + 隔离记录 + 导入报告
→ createMemoryWechatPayBackend(规范化种子)
→ 微信页面与知银共同读取该测试后端
```

Excel 解析器不直接调用知银账单分析。只有成功进入统一微信后端的记录才能被两个应用读取。

### 4.3 数据快照

每次授权读取返回：

```ts
type FinancialSourceSnapshotV2 = {
  provider: 'wechat_pay';
  snapshotId: string;
  sourceRevision: number;
  syncedAt: string;
  coverage: {
    from: string | null;
    to: string | null;
    total: number;
    returned: number;
    complete: boolean;
    nextCursor?: string;
  };
  transactions: NormalizedTransaction[];
  quality: {
    invalid: number;
    duplicate: number;
    quarantined: number;
    warnings: string[];
  };
};
```

微信页面和知银在一次对账或报告中必须使用同一个 `snapshotId`。数据更新后 `sourceRevision` 增加，旧报告标记为“基于旧快照”，不能假装实时。

## 5. 统一交易模型

建议保留提供方原始语义，再映射到分析语义：

```ts
type NormalizedTransaction = {
  id: string;
  provider: 'wechat_pay';
  nativeId?: string;
  occurredAt: string;
  direction: 'expense' | 'income' | 'neutral';
  kind: 'payment' | 'refund' | 'transfer' | 'red_packet' |
        'wealth' | 'withdrawal' | 'recharge' | 'other';
  amountCents: number;
  category: string;
  merchant: string;
  product?: string;
  fundingSource?: string;
  status: 'completed' | 'refunded' | 'partial_refund' |
          'failed' | 'pending' | 'unknown';
  merchantOrderId?: string;
  refundOf?: string;
  linkedId?: string;
  source: 'wechat_runtime' | 'xlsx_fixture' | 'manual';
  rawRow?: number;
};
```

规则：

- 金额只使用整数分；不能精确转成分的记录进入隔离区；
- 日期必须能解析且带时区；非法日期进入隔离区，不自动猜年份；
- 中性交易保留在流水和数据质量中，但默认不计入消费或普通收入；
- 原消费已退款时，原消费和退款都保留，通过 `refundOf` 关联；消费总额、退款额和净流出分别展示；
- 转账、红包、理财申赎、充值提现不混进日常消费；
- 商户、商品、备注等字段永远是不可信数据，进入模型前长度限制和转义；
- 导出到 CSV／Excel 时，文本以 `= + - @` 开头需添加安全前缀，防止公式注入。

### 5.1 ID 与去重

优先使用通过格式校验且在快照内唯一的微信交易单号。否则生成规范指纹：

```text
provider + occurredAt + direction + amountCents +
normalizedMerchant + product + merchantOrderId + status
```

相同指纹出现多次时保留出现序号，不能把真实的同日多笔付款误删。重复导入同一记录时用稳定指纹去重。原始 ID 无效时必须在质量报告中计数。

当前官方样本的日期是 Excel 数字日期，可确定性解析；无法解析的日期仍必须进入隔离区，禁止按文件名或相邻记录猜测。

## 6. 分页、覆盖和一致性门禁

### 6.1 分页要求

- 单页建议 200—500 条；
- 知银按游标读取至 `complete=true`，或明确以部分数据模式分析；
- 前端可只渲染当前页，但汇总必须来自同一快照的服务端聚合；
- 不允许对 1,971 条样本只取前 1,000 条后仍生成年度报告；
- 超时中断时保留已读取页数，页面显示覆盖范围和缺失数量，不输出完整结论。

### 6.2 对账控制量

每个快照至少生成：

- 总记录数、有效数、隔离数、重复数；
- 支出／收入／中性记录数；
- 消费总额、退款总额、转入、转出、中性资金变动；
- 最早／最晚有效日期；
- 按月记录数和金额；
- 规范化版本、分类规则版本、数据哈希。

微信页面与知银使用相同快照后，对上述控制量逐项比较。任一核心控制量不一致时：

1. 阻止生成“完整报告”；
2. 展示“数据尚未对齐”；
3. 记录差异字段和快照版本；
4. 不让模型猜测缺失部分。

### 6.3 测试层级

1. 解析器单测：字段、金额、日期、退款、中性交易、恶意文本；
2. 适配器合约测试：内存后端、真实 store 和 Excel 回放输出同一结构；
3. 对账测试：微信页面汇总与知银分析控制量一致；
4. 授权测试：无 `transactions` 权限时不能读取；撤销后立即失效；
5. 分页测试：1,971 条全部读取，缺页时明确不完整；
6. Agent 测试：模型只解释规范化结果，不接受账单字段中的指令；
7. 回归测试：退款、转账和中性交易不污染消费分类。

## 7. 客群设计

### 7.1 客群不是自动画像结论

账单只能产生可解释的需求信号，例如“固定支出占比较高”或“经营收款记录较多”。它不能证明用户是学生、已婚、老年人、高净值客户或小微企业主。

因此采用两层结构：

1. **用户确认客群**：用户主动选择，可有一个主客群和多个辅客群；
2. **需求标签**：描述希望知银帮助什么，可多选、可随时修改，不等同于身份。

### 7.2 客群与服务重点

| 客群 | 用户确认的典型特点 | 账单分析重点 | 理财操作重点 | 卡片管理重点 |
| --- | --- | --- | --- | --- |
| 年轻成长 | 学生、初入职场、年轻白领 | 分类、预算、超支、订阅和冲动消费线索 | 小额闲钱、目标储蓄、风险测评、产品对比 | 消费限额、订阅扣款、挂失、异常提醒 |
| 家庭 | 家庭共同支出、育儿、房贷等 | 家庭收支、房贷／教育／保险固定支出、年度账单 | 购房／教育／旅行目标，期限和流动性 | 多卡、大额提醒、境内外用卡、额度管理 |
| 财富管理 | 中高收入或较多可配置资金 | 收支与资产变化、闲置资金、大额交易核对 | 风险画像、产品筛选、持仓、申购／赎回辅助 | 大额支付、调额、境外支付、安全控制 |
| 银发安全 | 希望操作简单、强化安全 | 陌生商户、大额转出、异常频次重点提示 | 通俗解释、到期提醒、强化确认 | 一键锁卡／挂失、异常确认、敏感操作强化验证 |
| 商户／小微经营 | 个体经营、门店或小微企业资金管理 | 营收／支出、收款对账、退款异常、经营趋势 | 经营闲置资金、现金流预测、资金需求信息匹配 | 经营卡、员工／用途限额、大额支付、异常控制 |
| 通用 | 暂不选择特定客群 | 标准账单分析 | 标准风险测评和产品比较 | 标准卡片安全管理 |

上述特点只在用户确认后使用。财富管理客群不等同于高风险承受能力；银发安全不等同于能力不足；年轻成长不等同于低收入；商户客群不等同于可获得经营贷款。

### 7.3 需求标签

建议首期支持：

```text
budget_control       控制支出
goal_saving          目标储蓄
subscription_review  订阅管理
family_planning      家庭资金规划
liquidity            流动性管理
asset_allocation     资产配置
safety_first         强化安全
simple_explanation   通俗解释
business_reconcile   经营对账
cashflow_forecast    现金流预测
```

需求标签比客群更适合驱动功能。比如家庭用户也可以选择“强化安全”，年轻用户也可以选择“经营对账”。

## 8. 客群长期记忆模型

### 8.1 与现有记忆的关系

现有系统包含：

- `MemoryItem`：用户确认的偏好、习惯、目标、背景；
- `Profile`：沟通、音乐、交通、餐饮、购物五类日常印象；
- 独立业务状态：余额、账单、订阅、银行卡、风险测评等。

客群不应塞进日常印象，也不应从自由文本记忆中临时猜测。MVP 为了兼容现有私有记忆文件，在 v1 中新增可选结构化 `customerContext`；后续加入辅客群、目标和来源证明时再做 v2 无损迁移。

### 8.2 建议结构

```ts
type CustomerSegment =
  | 'general'
  | 'young_growth'
  | 'family'
  | 'wealth_management'
  | 'silver_safety'
  | 'merchant_sme';

type CustomerContext = {
  enabled: boolean;
  primarySegment: CustomerSegment;
  needs: CustomerNeed[];
  updatedAt: number;
  expiresAt: number;
};
```

MVP 只保存上述字段。`secondarySegments`、`goals` 和完整 `provenance` 保留为后续扩展，不在界面上伪装已实现。

### 8.3 写入规则

- 默认关闭；用户进入“我的 → 管理记忆 → 服务偏好”主动开启；
- 首次只展示选择题，不扫描账单后自动打标签；
- 系统可以根据账单显示待确认建议，例如“是否希望重点关注固定支出？”，用户点击确认后才写入需求标签；
- 账单只保存建议依据的规则名称和时间范围，不保存原始交易到长期记忆；
- 主客群、辅客群、需求标签、目标均可单独查看、修改、暂停和删除；
- 客群资料建议 365 天复核一次；目标按自身期限或 90 天复核；
- 用户选择“通用”或关闭后，不再把客群上下文发给模型；
- 删除后物理删除内容，不保留隐藏画像。

### 8.4 禁止写入长期记忆

- 当前余额、具体交易、完整账单、卡号和支付方式；
- 根据账单推断的年龄、收入、负债、婚姻、健康或经营身份；
- 风险等级、产品适当性、授信结果和交易授权；
- “以后所有操作免确认”等绕过安全边界的偏好；
- 模型自行生成、用户没有确认的客群标签。

### 8.5 上下文使用规则

模型收到的是有界摘要，例如：

```json
{
  "primarySegment": "family",
  "needs": ["family_planning", "safety_first"],
  "goals": ["为一年后的教育支出准备资金"],
  "status": "用户确认资料"
}
```

使用方式：

- 账单分析优先展示与需求标签相关的视图，但仍提供完整标准入口；
- 理财解释可调整期限、流动性和表达重点，但风险测评和适当性规则不能被客群覆盖；
- 卡片管理可强化安全提示或简化表达，但不能减少必要确认；
- 当前用户问题优先。与记忆冲突时询问并提供修改入口；
- 不把客群名称直接写进每条回复，避免标签化表达。

```ts
  merchant_sme: {
    billPriority: ['revenue_expense', 'reconcile', 'refund', 'trend'],
    investmentPriority: ['operating_liquidity', 'cashflow_forecast'],
    cardPriority: ['business_card', 'purpose_limit', 'large_payment'],
  },
};
```

这些配置只影响功能排序和说明重点。金额计算、异常规则、确认要求和金融适当性仍由统一业务规则决定。

## 10. 实施顺序

### 第一阶段：数据一致性（P0）

1. 为微信后端增加分页历史接口和快照版本；
2. 去掉两处静默 1,000 条截断，改成游标和 `complete`；
3. 扩展退款、中性交易、状态和覆盖信息；
4. 微信页与知银共享服务端聚合或同一纯函数；
5. 增加跨页面控制量对账测试；
6. 不完整时阻止完整月报／年报。

### 第二阶段：Excel 私有回放（P0 测试工具）

1. 建立本机 CLI 解析器，输入文件路径，输出临时规范化 fixture 和质量报告；
2. 默认不输出商户和备注到日志；
3. 损坏记录进入隔离区；
4. 将有效记录注入内存微信后端；
5. 同一用例同时验证微信页面和知银汇总；
6. 生成文件只放 `*.local.json` 或临时目录并由 Git 忽略。

### 第三阶段：客群用户确认（P1）

1. 新增 `customerContext` v2 schema 和无损迁移；
2. 增加服务偏好管理页；
3. 先支持主客群、需求标签和一个目标；
4. 写入必须有用户明确确认；
5. 接入三个场景的确定性展示配置；
6. 增加关闭、删除、过期、冲突和敏感推断测试。

### 第四阶段：账单信号建议（P1）

1. 只使用透明规则生成待确认需求建议；
2. 显示“为什么建议”和数据范围；
3. 不展示或保存身份推断；
4. 用户拒绝后记录该建议类型的冷却期，避免反复打扰；
5. 定期评估误建议率和用户撤回率。

## 11. 验收标准

### 11.1 微信账单一致性

- 对一个快照，微信页面与知银的总记录数、方向计数、消费、退款、转入、转出和月份控制量一致；
- 1,971 条用例不会静默变成 1,000 条；
- 非法日期和失真 ID 被隔离并计数，不自动修复成可信记录；
- 撤销授权后知银无法刷新微信账单，但微信自身账单仍可查看；
- 同一记录重复导入不重复计入；真实同日同金额多笔记录不会被误删；
- 数据不完整时页面和 Agent 均明确说明，不能生成完整年度结论。

### 11.2 客群长期记忆

- 默认无客群标签，未确认的账单信号不会写入；
- 用户可以选择多类需求，但只有一个主客群；
- 切换、关闭、删除后下一轮模型上下文立即更新；
- 客群不能改变风险测评、适当性、限额、授权或确认步骤；
- 对同一用户问题，客群只改变信息排序和解释方式，不改变基础金额和事实；
- 测试覆盖从账单诱导推断收入、年龄、家庭和风险等级的情况，系统必须拒绝保存；
- 用户说法与旧资料冲突时先询问，不按旧客群继续建议。

## 12. 测试数据管理

- 原始 Excel 始终位于仓库外；
- 自动化测试使用人工构造、去标识化的小型 fixture；
- 私有大样本只用于本机验收，测试报告只记录数量、校验结果和文件哈希；
- 不把真实昵称、商户、备注、卡尾号或交易单号放进 Issue、日志、截图和 PR；
- 提交前运行敏感文件检查，确认 `.xlsx`、转换后的 `*.local.json` 和临时报告未进入 Git。
