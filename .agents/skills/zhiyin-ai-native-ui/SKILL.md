# 知银 AI 原生 UI

这是用户对知银的产品约定，不是通用的“AI 风格”模板。新功能的第一版就要遵守，不能先做传统管理页，再附上聊天入口。宁宁、阿衡及后续管家适用同一交互原则，不把任何一位写死在业务组件里。

## 核心判断

**管家负责理解、整理和持续推进；用户负责表达意图、关键选择和必要授权。**

AI 原生不等于全屏文字聊天，也不等于渐变、发光边框或更多卡片。用对话推进事情，用适合信息的控件展示与调整方案。判断一个界面时，问：它减少了用户的操作和理解负担，还是只把传统表单换了入口？

## 一、从意图进入，不让用户先管理功能

- 用户说“给妈妈转钱”“记录今天的AA”“准备爱人生日”，管家识别并组织相应任务。不把“选任务类型、填任务名称、新建窗口”作为默认前置操作。
- 任务自然命名，如“给妈妈的生活费”“今晚聚餐AA”“爱人生日”；允许修改名称。任务类型、路由和上下文隔离是内部实现，不作为首屏管理控件。
- 默认在管家工作界面推进当前事情，不为每一步跳转新的业务页。管理入口、历史、完整编辑仍可保留，但不取代主要交互。
- 跨到微信、支付宝、商家支付等场景时，清楚说明下一步，并保留返回后可继续核对的同一任务。不能为了“连续”而隐藏平台授权或支付核对。

## 二、尽量少填表，但也不要变成问卷聊天

- 从用户已说的内容、当前任务和获准使用的记忆中整理已知信息；不重复询问，不要求把同一句话再抄到字段里。
- 缺少影响方案的信息时，在当前任务里追问。优先问此刻最重要的一两件事，不一次抛出所有字段，也不机械地逐字段问八轮。
- 能选择就提供合适控件：时间选择、联系人或群成员选择、金额快捷编辑、商品选项。始终允许自然语言补充，不把所有交互都限制成打字。
- 有必要的选择时给少量、明确、符合当前上下文的选项，通常2—4个；允许“你推荐”“暂时不决定”或自由补充，但只在这些答案有意义时提供。
- 推荐必须说明简短理由，并区分“建议”与“已确认”。已有地址、联系人、偏好只有确实可用时才提供确认入口；不假装拥有数据。
- 不明信息不能靠编造补齐。无确定联系人、账户、金额、日期等关键事实时追问；低风险假设可以先用于草稿，但要标明并在执行前核对。例如零散AA未说分法时可暂按平分，收款前集中确认。
- 完整表单放在“手动编辑/更多详情”等备用入口。紧凑的支付核对面板、设置、绑定资料和无法安全推断的输入可以保留表单，不机械地禁止所有字段。

## 三、同一任务是持续变化的工作现场

- 不只恢复聊天记录；还要恢复当前方案、已选项、已确认信息、执行状态、关联记录和待决定事项。
- “改成3000”“李娜半份”“不要鲜花”修改同一方案；不要另起一套卡片、任务或订单。突出修改带来的差异，不每次重讲全部内容。
- 任务窗口让人立即看懂**在做什么、现在怎样、还需要我决定什么**。例如“爱人生日 · 待确认地址”，比“筹备任务 · active”更有用。
- 多任务可以并行，当前任务有明确焦点，切换后回到各自现场。涉及归属不明确的补充，给出已有任务选项或追问，不擅自串上下文。
- 不要求真的创建子代理。遵守任务隔离与连续体验即可；本 skill 不规定后端架构。

## 四、界面按需要展开，不堆满模块

- 首页是连续的管家工作界面，不是把聊天塞进小卡片的功能大厅。身份与导航顶部固定，输入入口稳定，只有内容区域滚动。
- 无事时保持安静。不显示“0项订阅”“已检查微信/支付宝”“最近同步时间”等没有行动价值的填充信息，也不以监视式口吻展示连接状态。
- 只有需要用户处理、关注或回应的事件才进入显著位置。连接权限等说明放在对应设置或必要决策点，不反复占据首页。
- 信息紧凑成组，主结论、相关内容和下一步靠近。不用散落的大标题、分割面板和过大间距制造“高级感”。
- 方案可以有结构化组件，但不要卡片套卡片，或为每句回复都造一块独立容器。当前状态应有主次清晰的行动，不同时摆出一排同等权重的按钮。

## 五、解释简短，证据在需要时出现

- 先给有用的结论或建议，再按需展开原因与详情。页面已有金额、占比或列表，不在回复里逐项复读。
- 账单、分摊、趋势和资金影响用紧凑列表、图表或可编辑方案表达，不把大量 Markdown 表格变成竖屏“日期/金额/分类/备注”长条。
- 解释涉及具体交易、异常、重复订阅或周期判断时，才展示相关交易依据，明确来源和日期，并允许查看详情。不要因为用户喜欢过某次证据展示，就在每次回复强行放支付历史。
- 区分事实、推测与建议。缺证据就说需要核对；“其他”分类不等于异常，“两个音乐会员”也不自动等于浪费。
- 用记忆减少重复劳动，并尊重用户的选择。例如用户确认两个音乐会员都需要后，不持续劝取消；只有新变化有实际意义时再提出。用户可查看、更正和撤回偏好。
- 管家以自己的身份自然说话，不反复喊产品名称、不用品牌自夸句或冗长系统说明代替帮助。

## 六、体验主动，执行边界明确

- 清楚区分“正在理解”“方案待核对”“等待授权”“已执行”“失败待处理”。只展示实际发生的状态，不播放假步骤或假成功。
- 资金操作保留明确授权。最终核对金额、资金来源、收款对象/商家、执行时间及必要费用。关键修改后使旧授权失效，再核对，不把点击推荐选项当付款授权。
- 取消任务、取消订阅、撤销预约、释放预算和退款可能是不同动作，说明各自效果，不互相冒充。失败时保留方案和可恢复入口。
- 渠道、付款账户、预算预留和实际扣款分别说明。沙箱能力、前台提醒、后台调度和真实平台合作如实标明，不把未来能力写成已完成。
- 动画服务于任务切换、状态变化、金额调整和执行反馈；体现利落、连续的管家体验，不依靠无意义闪光、虚假等待或遮挡正文来“酷炫”。沿用当前品牌及用户选择的视觉方向，不由本 skill 强制更换配色。

## 新功能初版怎么使用

实现前先在工作计划中回答五件事，简短即可，不要求另外生成文档：

1. 用户会怎样自然提出这个需求？
2. 哪些信息已知，哪些确实必须问？
3. 管家如何推荐、给选项或提供合适的选择控件？
4. 当前任务怎样呈现可修改方案、关键证据和下一步？
5. 什么必须授权，怎样显示真实结果、失败恢复和返回现场？

先打通这条主路径，再补备用编辑/管理入口。只要求分析时不修改代码；开发时保留原有经典模式和已实现能力，不为套用原则无关重构。若使用其他 UI 技能，本 skill 约束知银的产品交互，其他技能负责视觉、可访问性和实现质量；遇到用户的新要求，以新要求为准。

## 两个行为示例

**生日筹备**：一句生日与预算需求 → 根据目录推荐组合 → 只补问尚未知的时间/收货信息 → 点选或直接说修改 → 就地显示方案与预算影响 → 明确授权后转商家核对付款。不要先展示八个必填字段加“保存”。

**零散AA**：“饮料18，午餐388平分，李娜饮料3元”逐次记入同一账本 → 收款时整理本次范围与规则 → 用成员选择与逐项分摊组件核对，必要时问歧义 → 用户确认 → 平台群收款 → 回到同一任务查看实际进度。不要让用户重抄所有消费、手填任务类型或另拉群。

## 交付前自查

- 第一入口是否要求先选类型、起名字或填大量字段？若是，重做主路径。
- 已知信息是否重复询问？选项是否真的随任务需要出现，而非固定快捷词？
- 直接表达修改与点选是否更新同一份方案？切换任务是否恢复完整现场？
- 首页是否有无意义的“已检查”、零项统计或大块占位？
- 结论、数字和回复是否重复？证据是否只在支撑当前解释时展示？
- 用户是否清楚下一步，以及什么只是建议、什么已经执行？
- 资金与破坏性操作是否经过明确核对，失败是否保留现场？
- 手机是否可读、紧凑、触控友好，没有隐藏必要操作或把正文压成碎片？

汇报时说明这次减少了什么用户负担，以及仍需填写/确认的内容与理由。不要仅声称“符合AI原生”而不给出实际交互依据。
